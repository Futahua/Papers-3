# USB route and remote folder latency — 17 October 2026

The creator reported roughly ten seconds opening a remote phone folder despite USB attachment. At diagnosis the renderer updates were installed, but the USB-capable desktop host was still pending installation. Idle owner probes measured about 100–150 ms for identity/stat/list operations; they did not reproduce the complete UI delay.

`UsbPeerTransport` discovers an authorized USB device with official `adb -d`, creates its own forward and reverse ports, verifies the already-paired phone owner through the existing bearer credential, and enables the cable route. An owner-restricted loopback HTTP proxy gives Android a reverse route to its paired PC. Android uses standard ProxySelector behaviour and a bounded lease. Existing network pairing remains unchanged. The Windows route and tus adapter retain logical owner URLs and journals while changing physical connections. No uncertain operation is replayed by the route selector. Transfer recovery remains with tus and the existing checked publication owners.

The build includes adb.exe, its two Windows libraries, NOTICE.txt and source.properties from the creator's installed official Android platform-tools. LapDog had no adb SDK installation. Runtime discovery prefers the packaged tools. The protocol uses official adb forward/reverse sockets: https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md

Remote path resolution also lacked in-flight request sharing. A regression check starts 24 simultaneous metadata/navigation lookups: it now makes three owner listing calls rather than 72. Existing two-second fresh-listing bounds remain; mutation invalidation retires both cached and pending generations.

Validation before install: TypeScript passed; 15 USB/tus/path/reachability tests and eight client/reload/service tests passed. One pre-existing client test was updated to assert the accepted stale-listing grace period rather than immediate offline flicker; the separate reachability test verifies sustained disconnection still becomes offline.

Activation uses the existing registered reload handler and its document flush/checkpoint barrier. The supported NSIS installer runs after process exit, with verified profile/Backpack/app backups and before/after content checks. The updater then resumes Papers with the handler's own reload arguments. No mouse or keyboard input is injected. ## Catalogue contention and direct checked browsing, 17 October 2026

The actual running Poordroid panes reproduced successful three-item listings at 3184, 12339, 11551 and 11837 ms. The phone rebuilt and atomically wrote its entire 1,648,290-byte resource catalogue in every HTTP worker's finally block. This was separate from indexed file metadata and consumed worker/storage capacity during ordinary reads.

Changed mappings now mark a generation and schedule one bounded delayed background save. Unchanged registrations do not schedule or write. A dedicated lock serializes catalogue saves, outside the shared phone-owner monitor. Checked jobs explicitly flush mappings before becoming durable; close flushes remaining mappings. HTTP cleanup closes the connection without rewriting the catalogue. PhoneCatalogCheck passed: twelve unchanged reads caused zero writes (1179 ms including its 700 ms settle), and a newly registered own fixture mapping survived owner restart. Its empty fixture was removed using its UUID/prefix guard.
